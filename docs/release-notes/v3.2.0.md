# Rust-Java REST Framework v3.2.0

`v3.2.0` is a stable release focused on production use: lower RSS profiles, clearer route-level
tuning, safer overload behavior, startup visibility, richer documentation, and copy/paste REST
examples.

The programming model does not change. Your handlers, services, components, request records, response
records, DB code, and business logic stay in Java. Rust continues to own the HTTP I/O plane, bounded
native memory, file streaming, WebSocket transport, and selected serialization-heavy paths.

## What Is New For Users

- New profile guidance for `micro-rest`, `micro-dubbo`, `low-rss`, `balanced-dubbo`, `throughput`,
  `fast-start`, and `ready-low-latency`.
- Route-level admission control with `@RouteAdmission` and property overrides.
- `JsonProducerResponse` for heavy dynamic JSON without building a Java DTO list graph.
- Direct JSON writer examples with `JsonBufferWriter`.
- Direct primitive query/path binding examples for hot numeric parameters.
- `RawResponse`, `JsonProducerResponse`, and `FileResponse` now cache encoded headers on hot paths.
- Startup diagnostics and optional startup indexes are documented.
- REST cookbook in README now includes GET, GET by id, POST payload, PUT update, PATCH, DELETE,
  request params, path variables, headers, and curl examples.
- Release package includes native Windows and Linux binaries for native ABI `20`.

## Which Profile Should I Pick?

| Profile | Use when | Practical effect |
|---------|----------|------------------|
| `micro-rest` | Small REST service, Dubbo off, memory is first priority | Lowest REST profile; controlled `503` under route pressure |
| `micro-dubbo` | REST service with native Dubbo consumer enabled | Small Dubbo footprint; prefer static provider list |
| `low-rss` | General memory-first REST service | More headroom than `micro-rest` |
| `balanced-dubbo` | Dubbo calls need smoother p99 | More worker/connection headroom, higher RSS |
| `throughput` | Dedicated high-RPS service | More retained buffers and workers |
| `fast-start` | Startup-sensitive service | Startup optimization defaults |
| `ready-low-latency` | First requests should be warm | Prewarm-oriented, may retain more warm state |

Small REST starting point:

```properties
reactor.runtime.profile=micro-rest
reactor.rust.http.max-connections=512
reactor.rust.http.max-inflight-response-bytes=8388608
reactor.rust.native-cache.max-entries=0
reactor.rust.native-cache.max-bytes=0
```

Small REST + Dubbo consumer starting point:

```properties
reactor.runtime.profile=micro-dubbo
reactor.dubbo.enabled=true
reactor.dubbo.transport=native
reactor.dubbo.providers=provider-host:20880
reactor.dubbo.native-connections-per-endpoint=1
reactor.dubbo.native-async-workers=1
reactor.dubbo.max-inflight=32
```

## Which Response Path Should I Use?

| Route type | Recommended path | Use it when |
|------------|------------------|-------------|
| Normal CRUD/business API | Record DTO | The response is normal business JSON |
| Already serialized JSON | `RawResponse.json(byte[])` | JSON already exists in Redis/read model/RPC result |
| Repeated immutable JSON | `RawResponse.registeredJson(...)` + `@NativeStaticRoute` | Same body is reused until restart |
| Repeated dynamic read model | Native dynamic cache | Cache key and TTL are explicit |
| Heavy fixed-shape JSON | `JsonProducerResponse` or `JsonBufferWriter` | DTO graph allocation dominates p99/RSS |
| Large export/download | `FileResponse` | File bytes should not pass through Java heap/JNI body frame |

Important: native cache is not a global response cache. Use it only when cache hits are expected and
invalidation is clear.

## Route Admission Example

```java
@RustRoute(method = "GET", path = "/reports/heavy", requestType = Void.class, responseType = JsonProducerResponse.class)
@DirectQueryInt(value = "items", defaultValue = 100, min = 1, max = 1000)
@RouteAdmission(maxConcurrent = 80, queueTimeoutMs = 150)
public JsonProducerResponse heavyReport(int items) {
    return JsonProducerResponse.ok(new HeavyReportProducer(items));
}
```

Property override:

```properties
reactor.rust.route-admission.get.reports.heavy.max-concurrent=80
reactor.rust.route-admission.get.reports.heavy.queue-timeout-ms=150
```

This protects the whole process from one expensive endpoint. A bounded `503` is intentional when a
low-memory profile is saturated.

## Memory And RSS Guidance

Measured release-gate memory proof:

| Metric | Value |
|--------|------:|
| Baseline RSS | 66.11 MiB |
| Peak RSS during mixed load | 91.35 MiB |
| Final idle RSS after load | 75.59 MiB |
| Final minus baseline | +9.48 MiB |

Practical memory sizing:

| Service shape | Starting pod memory |
|---------------|--------------------:|
| Tiny low-traffic REST, no RPC/DB | 96 MiB |
| Small REST with normal JSON | 128 MiB |
| REST + native Dubbo consumer | 128-160 MiB |
| Heavy dynamic JSON | 160 MiB or more, then measure |
| Large file/download routes | Size by stream concurrency and file chunk settings |

Do not set the pod limit exactly at the lowest idle RSS. Leave room for native buffers, thread stacks,
class metadata, request bursts, and JIT/runtime state.

## Release-Gate Benchmark Snapshot

At concurrency `512`, repeat `3`, `micro-rest-plus` benchmark recipe:

| Workload | Rust-Java avg RPS | Rust-Java p99 | Rust-Java avg RSS | Spring avg RPS | Spring p99 | Spring avg RSS |
|----------|------------------:|--------------:|------------------:|---------------:|-----------:|---------------:|
| Small JSON | 9153 | 115.83 ms | 68.75 MiB | 3459 | 368.60 ms | 314.33 MiB |
| Raw/precomputed JSON | 9659 | 114.80 ms | 68.56 MiB | 3875 | 623.98 ms | 274.13 MiB |
| Dynamic DTO JSON | 3338 | 309.68 ms | 67.82 MiB | 1524 | 776.47 ms | 309.98 MiB |

Read this correctly:

- Small JSON and raw/precomputed JSON are the strongest general-purpose paths.
- Dynamic DTO is supported and still lower RSS than Spring in this run, but it keeps Java object graph
  cost. Hot heavy DTO routes should move to `JsonProducerResponse`, direct writer, raw/precomputed
  JSON, or native cache depending on the real access pattern.
- At c1000, low-memory profiles may intentionally return `503` to protect RSS and p99. Use route
  admission, workload-specific profile tuning, or a larger pod budget for that class of traffic.
