# v3.1.0-rc3 - UTF-8 Request Annotation Patch

This release candidate keeps the Java programming model unchanged and fixes the next pilot issue:
Turkish and other non-ASCII values in request URL components are now decoded consistently before
they reach Java handler parameters.

Controllers, handlers, services, components, and business logic still stay in Java. Rust continues to
own the HTTP I/O plane and native response handling.

## What's New For Users

- `@PathVariable` now decodes UTF-8 percent-encoded values.
- `@RequestParam` now decodes UTF-8 percent-encoded values.
- Query parameters now treat `+` as a space, while path variables keep `+` as a literal plus.
- `@CookieValue` now works on the hot annotated invocation path and decodes UTF-8 cookie values.
- Middleware query helpers and WebSocket path/query parameter maps follow the same UTF-8 decode rules.
- Header lookup is safer under Turkish JVM locale because internal header key normalization now uses `Locale.ROOT`.
- The response UTF-8 behavior from `v3.1.0-rc2` remains in place.

## Changelog

- Added a small `UrlCodec` with a no-allocation fast path when no URL decoding is needed.
- Updated `HandlerRegistry` annotated parameter parsing for `@PathVariable`, `@RequestParam`, and `@CookieValue`.
- Updated legacy `ParameterResolver` parsing for compatibility paths.
- Updated middleware and WebSocket parameter parsing.
- Replaced remaining production `toLowerCase()` calls with locale-stable `Locale.ROOT` normalization.
- Added regression tests for Turkish URL components in path variables, query parameters, cookies, middleware, and WebSocket handshake params.
- Updated package version to `3.1.0-rc3`.

## Production Note

Use this RC instead of `v3.1.0-rc2` if your APIs receive Turkish or other non-ASCII values through
URL path variables, query parameters, cookies, middleware query access, or WebSocket params.
