# 4.8.1 — ARM64 Packaging Fix

[English](v4.8.1.md) | [Türkçe](v4.8.1.tr.md)

Stable patch release dated 2026-10-30. Upgrade from 4.8.0 as described below.

## Who Should Upgrade?

Applications using Linux ARM64 or macOS ARM64 should use this patch.
The 4.8.0 JAR contains current ARM binaries but stale platform manifests.
The loader correctly rejects that mismatch before loading the native library.

Use REST and platform `4.8.1` together. If you use cache, align it to `0.9.1`.
Sample services use `0.8.1`, model `0.5.1`, and utility `0.5.1`.
Use Dubbo `0.9.1` for the aligned REST dependency. Spring Dubbo `0.8.1` adds
generated consumer method/reference timeouts. Agent stays at `0.7.1`.

## What Changes?

- Regenerate ARM platform manifests from the actual packaged binaries and the
  coordinated source revision `3418671b5010afb5dc049897f2a7287dc6a58daf`.
- Verify every packaged JAR binary against the manifest selected by the loader,
  including platform sidecars. A mismatched sidecar fails the package gate.
- Keep ARM evidence explicit: `current-source-compile-verified` and
  `runtime.verified=false`. Linux ARM64 targets GLIBC 2.17.

No native rebuild, binary replacement, Java API or ABI change is involved.
Windows x64 and Linux x64 binary bytes are unchanged. Contracts remain REST 29,
Dubbo 7, Spring Dubbo 3, Redis 6 and Glowroot 6.

## Upgrade

Change your platform parent/BOM or REST dependency to `4.8.1`, and cache to
`0.9.1` if used. Rebuild the application. Keep the native resources supplied by
those JARs; do not replace only the manifest or mix a different native file.
Optional features retain their existing defaults. This packaging fix does not
claim new RPS, p99 or RSS improvements, or ARM runtime qualification.
